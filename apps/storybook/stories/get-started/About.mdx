# About the design system

The EventPipe Design System is the single source of truth for UI patterns, components, and tokens across EventPipe products.

---

## Mission

> Build a token-driven, accessible component library that lets product teams ship consistent, high-quality interfaces without reinventing shared patterns.

The design system is not a constraint — it is a shared vocabulary. When teams share components and tokens, they can focus effort on product differentiation rather than recreating buttons and dialogs.

## Architecture decisions

| Decision | Choice | Rationale |
|---|---|---|
| Base library | MUI v5 | Battle-tested behavior, strong a11y, wide ecosystem |
| Token format | Style Dictionary + custom transforms | Produces CSS custom properties compatible with all rendering targets |
| Token layers | Primitive → Semantic → Component | Enforces separation of raw values, design decisions, and component defaults |
| Styling | `styled()` + `PaperProps.sx` for portals | MUI's emotion-based API; portal surfaces require CSS vars (not ancestor selectors) |
| Language | TypeScript + React 18 | Full type safety; all props typed with explicit interfaces |

---

## What is and isn't the design system

**Is:**
- Components in `@eventpipe/ui`
- Tokens in `@eventpipe/tokens`
- Contracts in `docs/contracts/`
- Patterns in `docs/specs/`

**Is not:**
- Application layout code
- Business logic
- Page-level routing
- Backend API clients
